# Architecture decisions

This file records how the design notes (`source-notes/`) were turned into
code: every choice between conflicting notes, and every place the code
deliberately differs from a note. Anything not listed here follows the notes.

## Which note wins

The notes reuse part numbers across folders (Implementation Spec Parts 1–19,
Backend Parts 20–26, Frontend Parts 27–31, Database Parts 31–42). Precedence,
highest first:

1. This file.
2. **Backend** notes (Parts 20–26) — the newest implementation blueprint.
3. **Database** notes (Parts 31–42, Master V1 consolidated).
4. **Implementation Technical Specification** Parts 1–19 and "Remaining Architecture Foundation".
5. **Domain architecture** notes (Phase 1, Parts 3–30).

## Decisions

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                            | Notes / reason                                                          |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| D1  | Modular monolith, one MySQL 8 database, `tenant_id` on tenant-owned tables. No database-per-school.                                                                                                                                                                                                                                                                                                                                 | Master V1 §30, Part 21                                                  |
| D2  | Tenant = School. No campus entity in V1.                                                                                                                                                                                                                                                                                                                                                                                            | Master V1 §4                                                            |
| D3  | Stack: Node 22, TypeScript, Express 5, MySQL 8, Redis, BullMQ, Zod 4, JWT access tokens + rotating refresh sessions, OpenAPI generated from route definitions.                                                                                                                                                                                                                                                                      | Part 23                                                                 |
| D4  | **Drizzle instead of Prisma.** Prisma downloads engine binaries from `binaries.prisma.sh`, which is blocked where this project is built and tested. Drizzle is pure TypeScript with the same schema-as-code and SQL migrations. **Services own their queries** (no separate repository classes yet); every tenant query filters by the context tenant. A shared tenant-scoped query helper is planned before Phase 2 modules.       | Part 23 names Prisma and repositories                                   |
| D5  | **MySQL only.** The old memory and MongoDB adapters are dropped: transactions, foreign keys and tenant-aware constraints are part of the design.                                                                                                                                                                                                                                                                                    | Agreed with Vishnu, 29 Sep                                              |
| D6  | **Applied in place:** the platform core replaces the foundation of `api/`. The old JavaScript modules live in `legacy/` only as a porting reference and are removed as each module is rebuilt.                                                                                                                                                                                                                                      | Agreed with Vishnu, 29 Sep                                              |
| D7  | **Web admin is Flutter (web target)**, `admin-panel-repo`, not React.                                                                                                                                                                                                                                                                                                                                                               | Agreed with Vishnu (overrides Part 27)                                  |
| D8  | Permission codes are `domain.resource.action` with `read`: `students.read`, `fees.payments.create`. Platform permissions start with `platform.`.                                                                                                                                                                                                                                                                                    | Part 24 / Part 26 §26.14 over Part 4 (`student.view`)                   |
| D9  | Every permission belongs to a feature; the route layer requires the school's entitlement to that feature automatically. `core` is always entitled. Check order: permission, then entitlement.                                                                                                                                                                                                                                       | Part 4 §4.13, Part 24 §18                                               |
| D10 | Roles are data. System roles are platform-controlled; schools create custom roles (e.g. "Sub Admin"). No code checks role names (ESLint rule). Role lifecycle is ACTIVE/ARCHIVED; archiving takes effect immediately.                                                                                                                                                                                                               | Part 4, Part 26 (DRAFT/DISABLED states deferred)                        |
| D11 | Anti-escalation: nobody can grant, remove, suspend or edit anything carrying permissions — or a scope — wider than their own. Tenant roles only hold tenant permissions.                                                                                                                                                                                                                                                            | Part 24 §19                                                             |
| D12 | Scope lives on the role assignment (`ALL_TENANT`, `ASSIGNED_SECTION` + `{section_ids}` …); domain modules narrow queries with `scopesFor()`.                                                                                                                                                                                                                                                                                        | Part 31 §31.19, Part 26 §26.17                                          |
| D13 | Platform staff act inside a school only with `X-Tenant-Id` **and** `platform.tenants.access`, whose scope is `ALL_TENANTS` or `SELECTED_TENANTS` (`{tenant_ids}`). Inside the school only tenant permissions apply; audit rows say `PLATFORM_USER`. A school that is not ACTIVE is **read-only** for platform staff; recovery uses the platform school actions.                                                                     | Part 8 §8.13–8.15, Impl Part 2 §51–52                                   |
| D14 | School lifecycle: REQUESTED → UNDER_REVIEW → APPROVED → PROVISIONING → ACTIVE ⇄ SUSPENDED → ARCHIVED. Archive is restorable (to SUSPENDED) by a platform user allowed to archive. School lifecycle and subscription lifecycle stay separate.                                                                                                                                                                                        | Part 6, Master V1 §12, Impl Part 2 §53                                  |
| D15 | Subscription access modes: `FULL` (trial / active / past-due in period), `GRACE` (the notes' 30-day _recovery_ window: only users holding `tenant.subscription.read` — i.e. school admins — can enter, core features only), `LOCKED` (no entry, data kept). A replaced subscription becomes `SUPERSEDED`; `CANCELLED` means a real cancellation (at period end or immediately).                                                     | Master V1 §11, Part 7 §7.15, §7.23                                      |
| D16 | Entitlements are resolved from source rows (PLAN / ADD_ON / CUSTOM_CONTRACT / ADMIN_OVERRIDE, GRANT or DENY) by one pure resolver with the dependency graph. Any change that would switch off features the school has today — deny, removing a grant, downgrading — needs `confirm: true` and reports the impact. Disabling never deletes data.                                                                                     | Part 5 §5.13, Master V1 §9 (V1 allows DENY)                             |
| D17 | Error codes follow Part 22: `FEATURE_NOT_ENABLED` (not `ENTITLEMENT_REQUIRED` / `FEATURE_DISABLED`), `INVALID_STATE` and `OPERATION_NOT_ALLOWED` (not `BUSINESS_RULE_VIOLATION`), `INTERNAL_ERROR` (not `SYSTEM_ERROR`). Added: `INVALID_CREDENTIALS`, `ACCOUNT_LOCKED`, `ACCOUNT_DISABLED`, `SCHOOL_SUSPENDED`, `SCHOOL_NOT_ACTIVE`, `SUBSCRIPTION_EXPIRED`, `CONTEXT_SELECTION_REQUIRED`, `CONFIRMATION_REQUIRED`.                | Part 22 §23                                                             |
| D18 | Users reach schools through memberships (`users` has no `school_id`). School users are managed at `/members` (memberships, not global accounts). Current school: `/tenants/current`, `/tenants/current/settings`; switching: `/auth/switch-tenant`.                                                                                                                                                                                 | Part 31 §31.11, Part 24 §7, Impl Part 1 §32                             |
| D19 | One-time tokens (invitation, password reset) are generated by the email worker, sent, then stored only as SHA-256. Raw tokens never reach the database, outbox or production logs.                                                                                                                                                                                                                                                  | Part 24 §23                                                             |
| D20 | Sessions: 15-minute HS256 access JWT carrying only `sub`, `sid`, `mid`; permissions and entitlements are resolved per request (Redis, version-invalidated). Refresh tokens rotate; the **absolute** lifetime (30 days) is fixed at sign-in and a session idle for 7 days must sign in again. Reusing a rotated token revokes every session of the user. Refresh hash lives on `user_sessions` (no separate `refresh_tokens` table). | Part 24 §3–5 over Impl Part 1 §17–18                                    |
| D21 | Profile fields (name, contact, address) are on `tenants`; configuration (timezone, locale, currency, branding) is in `tenant_settings`.                                                                                                                                                                                                                                                                                             | Part 31 §31.10, Part 28 §28.12 (over Impl Part 2 §44 `tenant_profiles`) |
| D22 | API JSON is `snake_case`; dates ISO-8601 UTC; money integer minor units with a currency on every priced row; envelope `{data, meta}` / `{error:{code,message,details,request_id}}`.                                                                                                                                                                                                                                                 | Part 22 §21–23, Part 21 §1 (over DECIMAL in Impl Part 3)                |
| D23 | Background work: transactional outbox in MySQL → BullMQ (Redis) → idempotent handlers (`event_consumptions`). A durable MySQL `jobs` table for imports/exports is added with the first module that needs one.                                                                                                                                                                                                                       | Parts 23/25 over Part 31 §31.40                                         |
| D24 | V1 scope follows Master V1: HR/payroll, inventory/assets and calendar from the later backend blueprint are not in the Phase 1 catalog; adding them later needs no platform-core schema change.                                                                                                                                                                                                                                      | Master V1 §51                                                           |
| D25 | Default school settings are Indian (`Asia/Kolkata`, `en-IN`, `INR`, April academic year); all are per-school. Plan prices are **placeholders**.                                                                                                                                                                                                                                                                                     | Requirements doc                                                        |

## Deferred (planned, not forgotten)

- MFA (TOTP); separate email verification (invitation acceptance verifies email today).
- Platform billing: invoices, payments, webhooks, idempotency keys; add-on and custom-price flows (schema is ready).
- Sensitive-operation policy (`is_sensitive` is stored; reason / re-authentication / second approval not yet enforced beyond routes that already require a reason).
- Feature requests from schools; direct per-user permission overrides; permission dependencies; access reviews.
- Files service + object storage; real mail/SMS providers (`console` mail prints only in development).
- Redis-backed, tenant/user-aware rate limiting (current limiter is per process, auth routes only).
- Separate security-event stream (security events are in the audit log today).
- Platform role editing API, suspending platform users, CHECK constraints and composite tenant foreign keys.
