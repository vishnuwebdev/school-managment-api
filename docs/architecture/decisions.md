# Architecture decisions

This file records how the design notes (`source-notes/`) were turned into
code: every choice between conflicting notes, and every place the code
deliberately differs from a note. Anything not listed here follows the notes.

## Which note wins

The notes reuse part numbers across folders (Implementation Spec Parts 1–19,
Backend Parts 20–26, Frontend Parts 27–31, Database Parts 31–42). Precedence,
highest first:

1. This file.
2. **Backend** notes (Parts 20–26) — the newest implementation blueprint.
3. **Database** notes (Parts 31–42, Master V1 consolidated).
4. **Implementation Technical Specification** Parts 1–19 and "Remaining Architecture Foundation".
5. **Domain architecture** notes (Phase 1, Parts 3–30).

| D38 | **Attendance is a session with records, never a bare (student, date, flag).** `attendance_sessions` is the context (type DAILY or SUBJECT, year, class, section, date, optional subject offering, optional recorder teacher, optional period label, lifecycle); `attendance_records` is one student in one session with the `enrollment_id` it was marked under. Class, year and section on a session are derived from the section chosen, never trusted from the client. The database allows one DAILY session per year + section + date and one SUBJECT session per offering + section + date + period (generated `session_key` UNIQUE; the section is part of the SUBJECT key so a class-wide offering can be taken by several sections — a small deviation from note §33.30) and one record per student per session; every reference is a composite `(tenant_id, x_id)` foreign key. The register is the enrollment roster: an enrollment in that section and year with `start_date <= date < end_date` (end exclusive, because a class change opens the new enrollment on the day the old one ends); PENDING and CANCELLED enrollments never count. A DRAFT register follows enrollment live (students who joined appear; a student who left after being marked stays, flagged `on_roster: false`); once SUBMITTED or FINAL it is a snapshot of the marked students, so a later transfer never rewrites history. Attendance needs a section (a class-level enrollment without a section has no register). Non-working days and holidays are not modelled: a session can be opened for any past date of the active year (`tenant_settings.working_days` is not consulted yet). | Part 16 §16.3–16.28, Part 33 §33.13–33.34                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| D39 | **Statuses are per-school data, not booleans.** `attendance_statuses` has code, name, category (PRESENT, ABSENT, LATE, HALF_DAY, EXCUSED, LEAVE, OTHER), `counts_as_present` and `counts_as_absent` as decimals in 0.00–1.00 (sum ≤ 1), `requires_reason`, sort order, ACTIVE/INACTIVE, `is_system`. Every school gets six built-ins — PRESENT 1/0, ABSENT 0/1, LATE 1/0, HALF_DAY 0.5/0.5, EXCUSED 1/0 (reason required), LEAVE 0/1 (reason required) — created lazily and idempotently by `ensureDefaults(tenantId)` on every attendance read/write path (own autocommit statements, deadlock retry, per-process memo). ## D59 — Subscription billing: invoices and offline payments

- A school is invoiced by the platform for its subscription. Money is received offline (cash, bank transfer, cheque, card, mobile money) and **recorded by the platform team**; schools can only read it.
- `subscription_invoices` (status `OPEN | PAID | VOID`, minor units, `paid_minor` kept equal to the sum of RECEIVED payments) and `subscription_payments` (status `RECEIVED | REVERSED`, one receipt number each). Numbers are platform-wide: `INV-YYYY-NNNNNN` and `SRC-YYYY-NNNNNN` from `billing_sequences`.
- Starting or renewing a **paid** subscription (provision or change-subscription) creates the invoice in the same transaction; trials create none. Both calls accept an optional `discount_minor` and an optional `payment` so a payment already received is recorded at once. The subscription item stores the discounted final price.
- A payment may not exceed the balance. A payment cannot be edited: it is **reversed** (receipt kept, marked reversed) and the invoice reopens. An invoice with payments cannot be voided until they are reversed.
- School view: `GET /tenants/current/billing` (permission `tenant.billing.read`, core feature, School Admin only; works during the grace period). Platform view: `GET /platform/tenants/:id/billing`. Writes use `platform.subscriptions.manage`.
- PDFs: invoice (A4) and payment receipt (A5), issuer header from `BILLING_ISSUER_NAME` / `BILLING_ISSUER_DETAILS`; `BILLING_DUE_DAYS` (default 14).
- Events (outbox only, notifications later): `billing.invoice_issued`, `billing.payment_recorded`, `billing.payment_reversed`, `billing.invoice_voided`.
- Not built yet: automatic renewal invoices, overdue reminders, online payment.
